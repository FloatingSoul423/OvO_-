## ADR-01 公开检索候选与权威复核分离

**背景与问题。** 平台需按成果、学者、类型、年份和关键词组合检索，并支持稳定分页。成果可因纠错、归属争议或公开状态变化而撤销。仅对 RDS 业务表进行全文扫描，不利于组合检索和扩展；仅信任搜索索引，则异步刷新期间可能返回已撤销或未公开的对象。

**候选方案。** A：仅用 RDS 完成全文检索与排序；B：仅用 CSS 作为搜索与展示事实；C：CSS 返回公开候选 ID、版本及排序信息，API 再用 RDS 校验当前公开状态、版本和授权。A 简化组件但使文本检索与交易查询争用资源；B 读取快但无法把索引延迟与授权撤销隔离。

**决策。** 选择 C。CSS 仅保存可公开的检索字段，不存认领证明、内部审计或未生效修改。API 查询 CSS 后按 RDS 权威事实复核候选；复核失败的项不返回。CSS 不可用时明确报检索不可用，不能伪装为“0 条结果”。

**后果与代价。** 增加 RDS/CSS 两份读模型及索引维护成本；复核可能减少本页结果，续页需要绑定查询条件和稳定顺序。索引允许短暂滞后，撤销公开资格时仍须防止旧结果曝光。后续需确定分词、排序键和版本映射。

**验证与复审。** 用已公开、待审核、已撤销、版本更新及 CSS 故障样例核对搜索和详情。以课程认可的规模与并发口径测量错误率和 P95；没有实际压测前不写“已达标”。若数据库内建搜索足以满足经证实的工作负载，可复审是否继续使用 CSS。

## ADR-02 采集与 ETL 异步化，首期采用持久任务表

**背景与问题。** 外部来源可能限速、超时或中断；清洗、去重和身份消歧可能进入人工核验。把这些步骤放在用户请求中会占用连接，且失败后难以从检查点恢复。04 部署图已经将 ECS 模块化 API 与 ECS 后台 worker 画成不同节点。

**候选方案。** A：API 同步采集并处理；B：直接引入独立消息中间件；C：RDS 保存任务、批次、状态和检查点，由独立 worker 领取处理。A 无法隔离长任务；B 具备更强解耦潜力，但首期增加组件、运维和故障面。

**决策。** 选择 C。管理后台同步受理启动或停止命令，仅返回任务号；worker 按获准来源和许可范围限速读取，将可重读的原始批次写入 OBS，再登记 RDS 任务及 ETL 待办。ETL 依批次键与规则版本幂等处理，不确定记录进入人工核验。API 与 worker 逻辑隔离，初期可共用一台 ECS，负载需要时分机部署。

**后果与代价。** 任务表会产生轮询、锁竞争和积压，需监控最老待办时间、失败次数及检查点。对象写入失败不推进检查点；来源超时不得推断为成果删除或撤稿。后台无公网管理入口；来源访问须受限。若任务量与数据库负载证明持久任务表不足，再评估消息中间件。

**验证与复审。** 模拟外部来源超时、OBS 写入失败、RDS 事务回滚、worker 重启和重复批次；检查任务状态、重试与实体/出处不重复。核对采集时序图与状态图的停止、失败、重试语义。

## ADR-03 事实与发件箱同事务，派生视图异步更新

**背景与问题。** 一次成果变更可能同时影响 RDS 事实、CSS 检索和统计汇总。直接双写会出现 RDS 成功、CSS 失败或反向的半完成状态。认领审核的决定、对象级授权和审计又必须保持同一业务结果。

**候选方案。** A：请求中同步双写 RDS/CSS；B：只靠定时全量重建；C：RDS 事务内同时提交事实变化与 Outbox 事件，提交后由 worker 至少一次投递，消费者按对象版本幂等更新 CSS 与统计。A 有跨组件一致性风险；B 恢复简单但传播延迟与成本较高。

**决策。** 选择 C。RDS 是事实、授权、任务和审计的权威库。审核通过、门户授权和审计记录须在同一 RDS 事务生效；未提交成功时不展示通过。CSS 和统计是可重建投影，分别记录消费版本。旧事件不得覆盖新版本，版本缺口通过主库重建或人工处理。

**后果与代价。** 允许派生视图短暂延迟，须提供积压、失败原因、重放和对账入口。公开资格或授权已撤销时，不能仅等待索引刷新而继续暴露旧受限结果；查询还须执行 ADR-01 的主库复核。04 部署图中的“事实与事件”“公开索引刷新”应与此语义一致。

**验证与复审。** 在提交事务前后注入失败；暂停消费者后倒序、重复投递变更事件；检查审核状态、授权和审计一致，且搜索/统计最终按最新版本收敛。传播时延目标须从已批准 NF 基线取得，不能把候选值当实测值。

## ADR-04 统计汇总以权威事实为准并支持重算

**背景与问题。** 统计、热点、共同论文合作网络和最短合作路径须在合并、拆分、撤销与作者归属纠正后更新。每次在线请求扫描所有成果和关系会与查询争用资源；直接对事件做累计加减，重复消息或历史纠错可能导致总量漂移。

**候选方案。** A：每次查询实时扫 RDS 事实；B：从 CSS 直接聚合；C：按受影响实体和维度生成 RDS 汇总投影，记录输入版本，并允许从权威事实全量重算。A 对复杂图统计开销高；B 的索引滞后和公开字段范围无法充当全部事实来源。

**决策。** 选择 C。统计 worker 消费已提交的事实变更，按实体去重和已批准口径重算受影响汇总。合作边仅由符合公开条件的共同论文及有效作者关系支撑，每条边应能回查原论文。CSS 不作为统计事实源。07 两组过程记录中 OvO 强调可观察结果、CognitaNexus 强调证据与版本，最终由共同规则和数据样例确定计算口径。

**后果与代价。** 增加汇总表、输入版本和重算任务；界面需能说明统计更新时间。成员合并/拆分、论文撤销或关系纠错后可能短暂显示旧汇总，但不能把未确认关系算入公开合作路径。统计计算若成为资源瓶颈，可再评估专门计算组件。

**验证与复审。** 构造成果多来源、作者同名、合作边撤销、事件重复及倒序等样例，对照从 RDS 事实全量重算的结果；核对总量、排名、合作边及路径每一步的证据来源。
